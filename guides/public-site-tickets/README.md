# 公開サイト実装チケット

設計書: [public-site-design.md](../public-site-design.md)

このディレクトリは、設計書 §9
の実装フェーズを、実装・レビュー・受け入れが独立して行える単位に分割したものです。1チケットの大きさは、目安として「DB拡張マイグレーション（§10）」1本相当とします。チケットをまたぐ変更や、画面一式をまとめて完了扱いにすることは避けます。

## 共通の進め方

- TDDで、テスト方針に記載した振る舞い・契約のテストを先に追加し、実装。
- ディレクトリ配置やファイル移動だけを固定するテストは書かない。`tsc`、lint、formatterで検出できることもテストに重複させない。
- DBの確認は、プロジェクト指定の
  `docker compose exec -T postgres psql -U monden -d monden`
  を使う。サイトのビルド時だけDBへ接続し、閲覧時に接続しないことを確認する。
- 静的スナップショットは生成物であり、通常はgit管理しない。固定 fixture
  または一時ディレクトリでエクスポート契約をテストする。
- 画面チケットは、空データ・NULL・日付精度・モバイル幅のうち、対象画面に関係する欠損ケースを必ず含める。
- 各チケットの受け入れ時に、対象テスト、`bun run typecheck`、`bun test`、対象画面のスクリーンショット確認を行う。フィルタを持つ画面はURL直開きからの状態復帰も確認する。

## レビューで確定した横断契約

- 公開ページを持つ `project` / `person` / `composition` / `work` /
  `venue` / `event` は、export対象になる前に確定slugを持つ。slug欠落を
  画面側でUUIDや表示名にフォールバックして隠さない。
- exportは、固定した入力時刻を受け取る `snapshotGeneratedAt`、
  `schemaVersion`、内容ハッシュをmanifestに記録する。時刻を暗黙に現在時刻から
  取得して、同じ入力でもJSON差分が出る実装にはしない。
- 画面がURL状態を持つ場合、値はslugまたは列挙値を使う。複数値は同じquery keyを
  繰り返し、重複を除いて辞書順に直列化する。未知値は無視し、hash fragmentを
  保ったまま正規化する。個別の許可値はPST-018で定義する。
- `site:build` はPST-005、`site:export` はPST-006、`site:deploy` と
  `site:release` はPST-029がそれぞれ導入する。未実装の後続scriptを成功する
  ダミーとして先行チケットに置かない。
- client islandには操作に必要な最小データだけを渡す。Pagefindとnetworkの重い
  コードは、それぞれ検索画面・networkを実際に開いたときだけ読み込む。
