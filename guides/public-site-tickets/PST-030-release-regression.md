# PST-030 リリース候補の総合確認

- フェーズ: P5
- 対応箇所: 設計書 §3.4、§4、§8、§9
- 想定サイズ: マイグレーション1本相当
- 依存: PST-018、PST-021、PST-029

## 目的

設計書の主要導線と欠損データ規則を、リリース候補の実データで確認して公開可否を判断する。

## 実装範囲

- 全主要routeの静的生成、リンク切れ、404、anchor、画像の検査。
- フィルタ画面のURL直開き復帰。
- Dig再抽選、MM-DD lookup、networkトグル、reissueリンク、前後公演ナビ。
- NULL・live-only・未来event・孤立venue・track 0件の代表データ確認。
- desktop／mobileスクリーンショットと受け入れ結果の記録。
- slug変更時のリダイレクトmanifest、`/search`、資料室article anchorも代表ケースに含める。

## テスト方針

- 先に代表ケースを一覧化したE2E契約テストを追加し、ページのDOM配置に依存しない。
- 実DBからexportしたデータで、主要slugとリンクグラフを検証する。
- ブラウザのnetworkログで閲覧時のDB/APIリクエストが0件であることを確認する。
- 受け入れ記録にcommit SHA、snapshot hash、実行コマンド、確認URL、スクリーンショット、
  実施日、失敗時の戻し先チケットを残す。
- 失敗したケースはチケットへ戻し、受け入れ条件を満たすまでリリース扱いにしない。

## 受け入れ条件

- §3.2の全ルートが生成され、§3.4のリンク規約に反する行き止まりがない。
- timeline、discography、livesのURL直開きでフィルタが完全復帰する。
- `ANALYZE`、黄金の鐘、複数プロジェクト人物、孤立venueを含む代表回遊が完了する。
- NULLや0件を欠損エラーにせず、§8の表示ルールどおりに扱う。
- 受け入れ結果、スクリーンショット、実行コマンドをリリース記録に残す。
- 静的asset・Pagefind index・公開JSON以外への閲覧時リクエストは失格として記録する。

## 対象外

新機能の追加、データ内容の大規模修正、継続監視の自動化。
