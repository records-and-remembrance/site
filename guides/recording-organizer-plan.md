# 録音整理画面 実装プラン

## 目的

同じ楽曲を収録した複数のトラックについて、原則として同じ録音へまとめ、例外となる別録音だけを人間が分けられるようにする。

汎用的な `recording` CRUD ではなく、楽曲ごとに収録トラックを比較しながら「統合」「分割」「整理完了」を行う専用画面を提供する。

## 基本方針

- 同一楽曲のトラックは、初期判断では同じ録音として扱う。
- ライブ版、再録音、別アレンジなどの例外だけを人間が別録音へ分ける。
- 「同じ録音」は、複数の `track.recording_id` が同じ `recording.id` を参照することで表現する。
- 録音の同一性を表す新しい関連テーブルは追加しない。
- ドラッグ操作に依存せず、マウス、キーボード、タッチで利用できる選択式UIにする。

## 1. DBと整理状態

### `recording_review` テーブル

楽曲ごとの整理状況を保存する。

| カラム                   | 用途                                               |
| ------------------------ | -------------------------------------------------- |
| `composition_id`         | 対象楽曲。主キーかつ `composition.id` への外部キー |
| `assignment_fingerprint` | `track_id → recording_id` の現在の組み合わせ       |
| `reviewed_at`            | 整理完了日時                                       |

fingerprintは、対象楽曲に属するトラックを安定した順序で並べ、`track.id` と `track.recording_id` の組み合わせから生成する。

保存済みfingerprintと現在値が一致する場合だけ「整理済み」とみなす。トラックの追加や録音の紐付け変更が発生した場合は、自動的に「未整理」へ戻る。

## 2. 録音整理API

汎用管理APIとは分けて、録音整理用のAPIとリポジトリを実装する。

### 楽曲一覧

- 未整理／整理済みで絞り込める。
- 楽曲名で検索できる。
- トラック数と録音数を表示する。
- 未整理を優先して並べられる。

### 楽曲詳細

楽曲に属する録音グループと、各グループが参照しているトラックを返す。

トラックには次の表示情報を含める。

- リリース名
- 形式
- 発売日
- 曲順
- トラックの録音日
- メモ
- recordingに紐づくcontribution

### 録音の統合

入力:

- 統合先の `recording_id`
- 統合元の `recording_id` 一覧
- 人間が確定した統合後の録音メタデータ

処理:

1. 対象のrecordingがすべて同じcompositionに属することを検証する。
2. 統合元を参照するtrackを統合先へ移動する。
3. 統合元を参照するcontributionを統合先へ移動する。
4. 人物、役割、楽器、メモが完全に一致するcontributionを重複排除する。
5. 録音メタデータを更新する。
6. 参照されなくなった統合元recordingを削除する。

録音年、種別、録音日などに競合がある場合は、自動的に片方を採用しない。APIは競合を返し、画面上で人間が統合後の値を決める。

すべての処理を単一トランザクション内で実行する。

### 録音の分割

入力:

- 分割元の `recording_id`
- 新しい録音へ移す `track_id` 一覧
- 新しい録音のメタデータ
- 新しい録音へコピーするcontribution一覧

処理:

1. 選択したtrackが分割元recordingを参照していることを検証する。
2. 新しいrecordingを作成する。
3. 選択したtrackを新しいrecordingへ移動する。
4. 人間が選択したcontributionだけを新しいrecordingへコピーする。

分割元の全トラックを選択した場合は、新しいrecordingを作る意味がないため拒否する。

### 整理完了

現在の割り当てfingerprintを計算して `recording_review` に保存する。

## 3. 専用画面

管理画面のサイドバーに「録音整理」を追加する。

```text
左: 楽曲キュー          右: 録音グループ
──────────────────────────────────
未整理 96              録音 A
ミナソコ  8曲/8録音    □ LOW NAME #1
ANALYZE   7曲/6録音    □ BEST #2
                        □ 線 #5
                        [選択を録音Aにまとめる]

                        録音 B
                        □ festival M.O.N. #10
                        [選択を別録音に分ける]

                        [整理済みにする]
```

### 楽曲キュー

- 未整理／整理済みのタブまたはフィルター
- 楽曲名検索
- トラック数と録音数
- 現在選択中の楽曲
- 「次の未整理」操作

### 録音グループ

- recordingごとにトラックをグループ表示
- 複数トラックの選択
- 選択したトラックを既存録音へ統合
- 選択したトラックを新しい録音へ分割
- 録音メタデータの編集
- contributionの確認
- 整理完了

### アクセシビリティ

- React Ariaの `Table` または `GridList` を使用する。
- 選択、統合、分割をキーボードだけでも操作できるようにする。
- ボタンの無効理由と処理結果をテキストでも伝える。
- 保存中は関連操作を無効化し、二重送信を防止する。
- 確認ダイアログを閉じた後のフォーカスを元の操作位置へ戻す。

### データ取得

- 楽曲一覧と選択中の詳細を別クエリにする。
- 独立した取得処理は並列化する。
- 統合、分割、整理完了後は、一覧全体ではなく対象楽曲の詳細と集計を無効化する。
- 検索入力による重い再描画は必要に応じて遅延させる。

## 4. seed再生成対策

現在の `scripts/generate_work_seed_sql.ts` は、再実行時に `track.recording_id` を生成値へ戻すため、人間の整理結果が失われる。

生成処理を次のように変更する。

- 既存trackの `recording_id` は上書きしない。
- 新規trackの場合だけ、初期recordingを作成して割り当てる。
- 統合時に削除したrecordingを、孤立したrecordingとして再作成しない。
- タイトル、曲順など生成元の情報は、既存trackの他フィールドへ引き続き反映できるようにする。

この挙動は生成SQLの回帰テストで保証する。

## 5. TDDの進め方

各機能はテスト、実装、リファクタリングの順に進める。

### ステップ1: DBとドメイン処理

先に次の失敗テストを書く。

- 異なる楽曲のrecordingは統合できない。
- 存在しないrecordingやtrackは操作できない。
- 統合時にtrackとcontributionが失われない。
- 同一contributionだけが重複排除される。
- トランザクション途中の失敗時には変更が残らない。
- 分割元の全トラックを移す操作は拒否される。
- fingerprintが変化すると未整理になる。

その後、DB依存を先に受け取るカリー化関数として処理を実装する。

### ステップ2: API

先にルートテストを追加する。

- 一覧の検索、状態絞り込み、ページング
- 楽曲詳細
- 統合と分割の入力検証
- メタデータ競合
- 整理完了
- Not FoundとConstraint Violationのレスポンス

その後、専用ルートとバリデーションを実装する。

### ステップ3: UI

先に次の操作テストを書く。

- 未整理楽曲を選択できる。
- 複数トラックを選択できる。
- 統合確認とメタデータ競合を処理できる。
- 別録音として分割できる。
- 整理済みにできる。
- 次の未整理楽曲へ移動できる。
- キーボードで主要操作を完了できる。

その後、画面、APIクライアント、状態管理を実装する。

### ステップ4: seed生成

先に次の回帰テストを書く。

- 新規trackには初期recordingが割り当てられる。
- 既存trackの手動設定済み `recording_id` は変更されない。
- 統合で削除された初期recordingは再作成されない。

その後、生成SQLを変更する。

## 6. 検証

実装完了時に次を実行する。

```bash
bun test
bun run typecheck
bun run lint
bun run admin:build
```

さらにブラウザで実データを使い、次のシナリオを確認する。

1. 同じ楽曲の複数トラックを一つの録音へまとめる。
2. ライブ版だけを別録音へ分ける。
3. contributionの移動とコピーを確認する。
4. 整理済みにする。
5. seedを再生成しても整理結果が維持されることを確認する。

## 7. コミット単位

変更量の目安を見ながら、テストと実装を同じコミットへまとめる。

1. `録音整理APIとデータモデルを追加`
2. `録音整理画面を追加`
3. `録音の手動整理結果をseed再生成時に保持`

## MVPの完成条件

- 楽曲ごとに録音候補を確認できる。
- 複数の録音を安全に統合できる。
- 選択したトラックを別録音へ分割できる。
- contributionを失わずに扱える。
- 整理済み／未整理を管理できる。
- seed再生成後も人間の整理結果が維持される。
- マウスを使わず主要操作を完了できる。

録音候補の自動推測や、自動的な同一録音判定はMVPに含めない。
